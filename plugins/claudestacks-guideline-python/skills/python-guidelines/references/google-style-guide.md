# Python — Google Python Style Guide Index

Apply the [Google Python Style Guide](https://raw.githubusercontent.com/google/styleguide/gh-pages/pyguide.md) when writing or reviewing Python, with PEP 8 and PEP 257 as the baseline beneath it. Spirit over letter: understand the motivation before deviating. The full text and per-section rationale lives at the linked guide — fetch it when a rule is ambiguous in context.

Each item is identified by the guide's section number (`G-<section>`). Use these codes verbatim in commit messages, review comments, and PR descriptions when a change is motivated by a specific section (e.g. `"fix(api): drop the mutable default per G-2.12"`).

Where a `→` points at another reference, that file is the authority and states or enforces the rule (`references/strict-quality.md` enforces through the formatter or a Ruff family and does not restate it); the line here exists so the code stays citable. An entry marked **Departure** records where this guideline, or the gate, differs from the guide, with the words of the reference that governs.

**Source.** Codes, titles and numbers are those of the guide as fetched on 2026-10-30 with `curl -sS -L https://raw.githubusercontent.com/google/styleguide/gh-pages/pyguide.md` (4097 lines). That copy has no 2.15 and no 3.9, so a code cites the guide as it read on that date, not a stable numbering. Only the sections a reference or the gate applies are listed; for a section missing below no reference applies it and the baseline reports no violation of what it asks (probed on 2026-10-30), so the guide itself is its source.

**The formatter and linter claims** below were observed on 2026-10-30 with `uvx ruff@0.17.3 format --isolated --diff`, `uvx ruff@0.17.3 check --isolated --select I --diff` and `uvx ruff@0.17.3 check --isolated --extend-select` followed by the families of the `extend-select` list in `references/strict-quality.md`, on small probe files; `--isolated` reads no configuration, and the baseline sets no formatter option, so the defaults are the ones the gate runs.

## 2 Python Language Rules

- **G-2.1 Lint** — Run a linter over every change, and suppress a warning on the line that triggers it rather than hiding other issues. **Departure.** The gate runs Ruff and mypy, not `pylint`, and a suppression names a code. Google asks for an explanation only "If the reason for the suppression is not clear from the symbolic name, add an explanation"; `references/strict-quality.md` says "Every suppression carries a reason comment." → `references/strict-quality.md`
- **G-2.2 Imports** — `import x` for packages and modules, `from x import y` only where `y` is a module, `from x import y as z` only for a name clash, a long or generic name; no relative names, even inside the same package. Symbols from `typing`, `collections.abc` and `typing_extensions` are exempt. This entry is the home of the caller-side rule: `references/init-export-only.md` leaves it here ("How a caller imports is Google 2.2's rule, indexed in `google-style-guide.md`, not this file's."). **Departure.** `references/init-export-only.md` says "The re-export line is where this guideline overrides Google 2.2.": `from pkg.core import double` is allowed in `__init__.py`, and only there. → `references/init-export-only.md`
- **G-2.3 Packages** — Import every module by its full package name; never rely on `sys.path` to make a bare `import jodie` find a sibling. → `references/init-export-only.md` (absolute, not relative), `references/modularity.md` (no module named after a standard-library module)
- **G-2.4 Exceptions** — Built-in exceptions where they fit; no `assert` for validation; a library's own exceptions inherit from an existing exception class and end in `Error`; no bare or catch-all `except` outside a re-raise or an isolation point; a small `try` body; `finally` for cleanup. **Departure, stricter.** `references/errors.md` says "This is stricter than Google 2.4.": the guide's example raises `ValueError(f'Min. port ...')` at the raise site, which the baseline reports as `TRY003`, so the message lives in the exception class or is bound to a name first. → `references/errors.md`
- **G-2.5 Mutable Global State** — Avoid mutable module-level or class-level state; where it is warranted, make it internal with a leading `_`, give outside code functions to reach it, and explain the design in a comment. Constants in all caps are fine. `PLW0603` reports a `global` statement that updates a name (observed); it drew no finding on a module-level list mutated in place with `.append` (observed), so review holds that part. → `references/strict-quality.md` (the `PL` family selects `PLW0603`)
- **G-2.8 Default Iterators and Operators** — `for key in d` and `key in d`, not `d.keys()`. `SIM118` reports `"a" in d.keys()` (observed). → `references/strict-quality.md` (the `SIM` family selects `SIM118`)
- **G-2.9 Generators** — Fine to use; document them with `Yields:`, not `Returns:`. → `references/docstring-discipline.md` (the `Yields:` rule only)
- **G-2.10 Lambda Functions** — Okay for one-liners; prefer a generator expression over `map()` or `filter()` with a `lambda`, and `operator.mul` over `lambda x, y: x * y`. `C417` reports `map()` with a lambda (observed); `filter()` with a lambda and `reduce()` with a lambda drew no finding (observed), so review holds those. → `references/strict-quality.md` (the `C4` family selects `C417`)
- **G-2.12 Default Argument Values** — Never a mutable object as a default value. → `references/idioms.md`
- **G-2.13 Properties** — Only for cheap, unsurprising attribute access; do not use a property for a computation a subclass may want to override. → `references/protocols-and-composition.md` (the inheritance warning only)
- **G-2.14 True/False Evaluations** — Use the implicit false where possible, `is None` for a `None` check, and never `== False`. `E711` reports `x == None` and `E712` reports `flag == False` (observed); `if len(seq):` and `len(seq) == 0` drew no finding (observed), so the empty-sequence bullet is held by review. → `references/strict-quality.md` (the `E` family selects `E711` and `E712`)
- **G-2.19 Power Features** — Avoid custom metaclasses, bytecode access, import hacks and the like; standard-library modules that use them internally (`abc.ABCMeta`, `dataclasses`, `enum`) are fine. → `references/strong-types.md` (relies on the `dataclasses` and `enum` carve-out only)
- **G-2.20 Modern Python: from \_\_future\_\_ imports** — Google: "Use of `from __future__ import` statements is encouraged". **Departure.** `references/typing.md` says "At a 3.14 floor, no `from __future__ import annotations` and no quoted forward references." and "Below a 3.14 floor, a forward reference is a quoted name or the future import."; the gate fails a quoted name at a 3.14 floor (`UP037`), and review holds the rest. → `references/typing.md`
- **G-2.21 Type Annotated Code** — Annotate public APIs and type-check in the build. `references/typing.md` says the Google recommendation "is met and exceeded by `mypy --strict` in the gate". → `references/typing.md`, `references/strict-quality.md`, `references/strong-types.md` (cites the public-API sentence of 2.21 and says what the annotation on a domain value should be)

## 3 Python Style Rules

- **G-3.1 Semicolons** — No trailing semicolons, no two statements on a line. `ruff format` split `import os; import sys` and `x=1;y=2` onto separate lines (observed). → `references/strict-quality.md`
- **G-3.2 Line length** — Google: at most 80 characters, with named exceptions (long imports, URLs), implicit line joining rather than a backslash. **Departure.** `references/docstring-discipline.md` says "Google's 80 is not Ruff's default `E501` limit of 88"; the gate's limit is Ruff's, and review holds the 80-column docstring summary. → `references/strict-quality.md`, `references/docstring-discipline.md`
- **G-3.3 Parentheses** — Use them sparingly. `ruff format` rewrote `if (a):` and `return (a)` without them (observed). → `references/strict-quality.md`
- **G-3.4 Indentation** — Four spaces, never tabs. `ruff format` rewrote 2-space and 6-space blocks to four (observed). → `references/strict-quality.md`
- **G-3.5 Blank Lines** — Two between top-level definitions, one between methods, none after a `def` line. `ruff format` inserted the two blank lines before a top-level `class` and `def` (observed) but left a blank line after a `def` line in place (observed), so that part is not settled by the gate. → `references/strict-quality.md`
- **G-3.6 Whitespace** — Typographic spacing around punctuation and operators, no trailing whitespace. `ruff format` rewrote `[1,2 ,3]` to `[1, 2, 3]`, `foo(a ,  b)` to `foo(a, b)` and `def f(a,b = 2)` to `def f(a, b=2)`, and removed trailing whitespace (observed). → `references/strict-quality.md`
- **G-3.8 Comments and Docstrings** — A docstring on every public module, class and function, in the Google section layout; comments explain what the reader cannot see in the code. **Stricter than the guide's trigger:** `references/docstring-discipline.md` says "The gate demands a docstring on every public name whatever its size." The license-boilerplate paragraph of the guide's module-docstring subsection is applied by no reference. → `references/docstring-discipline.md`, `references/init-export-only.md` (a package's docstring)
- **G-3.10 Strings** — f-string, `%` or `format`, never `+` to format; no `+=` to build a string in a loop; a log call takes a literal pattern and its arguments, not an f-string. `references/idioms.md` holds the lazy-argument rule (an f-string log message drew no finding at any gate step, observed). `ruff format` rewrote `'single'` to `"single"` (observed), which the guide allows when a file is consistent. → `references/idioms.md`, `references/strict-quality.md`
- **G-3.11 Files, Sockets, and similar Stateful Resources** — Close them explicitly, preferably with a `with` statement or `contextlib.closing()`; where that is infeasible, document how the lifetime is managed. `SIM115` reports `open()` outside a `with` (observed); a `socket.socket()` that is never closed drew no finding (observed), so review holds sockets and the other resources. → `references/strict-quality.md` (the `SIM` family selects `SIM115`)
- **G-3.12 TODO Comments** — Google: `TODO(<context link>): <explanation>`. **Departure.** `references/docstring-discipline.md` says "`TODO: <what is missing>` states a gap in the code." and adds that no `TODO` rule is selected by the baseline; it asks for no parenthesized context. → `references/docstring-discipline.md`
- **G-3.13 Imports formatting** — One import per line, at the top of the file after the module docstring, grouped standard library, third party, then this repository, sorted within each group. **Departure.** Google sorts by "each module's full package path" and its example interleaves `from absl import app` with `import bs4`; Ruff's `I`, which the baseline selects, put every `import x` line before every `from x import y` line in the same group (observed), and the gate's order governs. → `references/strict-quality.md`, `references/init-export-only.md` (imports are sorted by Ruff's `I`)
- **G-3.14 Statements** — One statement per line. `ruff format` split `if a: return 1` and `def g(): pass` onto two lines (observed). → `references/strict-quality.md`
- **G-3.16 Naming** — Descriptive names, `lower_with_under` module and package names with no dashes, CapWords classes, exception names ending in `Error`. → `references/init-export-only.md` (naming sibling modules), `references/errors.md` (the `Error` suffix, `N818`), `references/strict-quality.md` (the baseline selects Ruff's `N` family)
- **G-3.18 Function length** — Prefer small, focused functions; the guide sets no hard limit and asks for a second look past about 40 lines. `references/modularity.md` sets no line count either: "A function can be under every size limit and still mix four concerns", so review splits a function that mixes concerns. → `references/modularity.md`
- **G-3.19 Type Annotations** — The guide's annotation rules, with several overridden. **Departure.** The guide lets a module be partly annotated (3.19.1), allows `Union` and `Optional` (3.19.5), writes aliases as `typing.TypeAlias` (3.19.6) and declares `TypeVar` at module level (3.19.10); `references/typing.md` answers with "every function annotated", "this guideline does not accept them", "`type` statement, `TypeAlias` banned" and "bracketed type parameters", and for forward declarations (3.19.3) see G-2.20. Where the guide and the reference agree, such as abstract container types from `collections.abc` (3.19.12), the reference states the rule. → `references/typing.md`
