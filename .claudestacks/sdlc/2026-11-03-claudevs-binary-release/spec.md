# Spec: Prebuilt `claudevs` releases and a Rust-free `airsl` install

This spec adds the binary release pipeline `airsl` and `buildl` already use, so `claudevs` installs
with one command and no Rust toolchain, and lets plugin users install and find the `airsl` runtime
without Rust. It covers `claudevs-cli` only, on six Unix targets. Probes ran on 2026-11-03 against
this repository at `b8d6eaa`, on macOS arm64. `airsl` and `buildl` citations are to their
default-branch source tarballs fetched the same day. `runner-images` citations are to its `main` branch
fetched the same day.

## 1. Premises

- All three crates are already published. crates.io API output: `airsclaude: 0.1.0`,
  `claudevs: 0.1.0`, `claudevs-cli: 0.1.0`. `git log <crate>-v0.1.0..HEAD -- crates/<crate> | wc -l`
  printed `0` for each.
- This repository has no GitHub release today: `gh release list -R airsstack/claudestacks -L 5`
  printed nothing.
- `claudevs-cli` declares the binary `claudevs` (`crates/claudevs-cli/Cargo.toml:17-19`). Its one
  native dependency is Lua: `cargo tree -q -p claudevs-cli -e normal --prefix none | grep -E
  '\-sys|openssl|aws-lc|^ring' | sort -u` printed only `mlua-sys v0.11.0`.
- `claudevs` needs `git` at runtime for any plugin with test cases. With only `sh` on `PATH`,
  `claudevs check minimal-plugin` printed
  ``claudevs: run git `/var/folders/.../.tmpvSmXJT`: No such file or directory (os error 2)`` and
  exited 2. The call is at `crates/claudevs/src/harness/project.rs:224`.
- `claudevs doctor` does not report that requirement: `grep -n -i git
  crates/claudevs/src/doctor.rs` printed nothing, while the same file's `claude binary` probe is at
  `doctor.rs:115`. By the author's decision, this release documents the requirement and does not change
  `doctor`.
- `claudevs` is not written to build on Windows: `crates/claudevs/src/wiring/invocations.rs:31` imports
  `std::os::unix::fs::PermissionsExt` with no `cfg`, and `:212` calls `.mode()` outside the test module
  that starts at `:284`. No Windows build was run.

## 2. Release pipeline

**`dist-workspace.toml`** is added at the repository root, with these settings and the explanatory
comments `buildl` carries (`buildl/dist-workspace.toml:1-36`):

```toml
[workspace]
members = ["cargo:."]

[dist]
cargo-dist-version = "0.33.1"
ci = "github"
installers = ["shell"]
targets = ["aarch64-apple-darwin", "aarch64-unknown-linux-gnu", "aarch64-unknown-linux-musl", "x86_64-apple-darwin", "x86_64-unknown-linux-gnu", "x86_64-unknown-linux-musl"]

hosting = "github"
install-updater = false

github-attestations = true
global-artifacts-jobs = ["./claudevs-cli-smoke"]
pr-run-mode = "upload"

[dist.github-custom-runners]
aarch64-apple-darwin = "macos-15"
```

**The custom runner departs from `airsl` and `buildl`.** dist's default for that target is `macos-14`
(`dist plan --output-format=json` in a scratch copy printed `"runner": "macos-14"` for
`aarch64-apple-darwin`). `gh api repos/actions/runner-images/issues/13518` reads: "GitHub Actions will
fully retire all macOS 14 images on November 2, 2026." `macos-15` is the arm64 label
(`runner-images/README.md:34`). With the setting added, the plan's runners were `macos-15-intel`,
`macos-15`, `ubuntu-22.04-arm` and `ubuntu-22.04`, and the setting's form is at
`cargo-dist v0.33.1 book/src/reference/config.md:1519-1531`. No job has run on `macos-15` for this
binary yet (section 10).

**The root `Cargo.toml`** gains the profile `airsl/Cargo.toml:77-79` carries:

```toml
[profile.dist]
inherits = "release"
lto = "thin"
```

**`crates/airsclaude/Cargo.toml`** gains `[package.metadata.dist]` with `dist = false`. Without it,
`dist plan` on a scratch copy announced a second release, listing `airsclaude 0.1.0` with
`[bin] airsclaude-agent-testchild` for every target. With it, `dist plan` announced only
`claudevs-cli 0.1.0`, with `[bin] claudevs` six times. Cargo accepts the key silently: `cargo metadata
--no-deps` exited 0 with an empty stderr. dist's reference says: "`dist = false` on a package can be
used to force dist to ignore it" (`config.md:197`).

**`.github/workflows/claudevs-cli-release.yml`** is generated by running `dist generate` (dist 0.33.1)
and is never edited by hand. `airsl/README.md:86-87` says so: "Change the config and run `dist
generate`; never edit the workflow by hand, or the release's plan step fails." A scratch run of
`dist generate` printed `generated Github CI to .github/workflows/claudevs-cli-release.yml`.

What that generated file does, read from the scratch output:

```
pull_request ─┐
              ├─► plan ─► build-local-artifacts ─┬─► custom-claudevs-cli-smoke ─┬─► host ─► announce
tag push ─────┘           (line 91)              │   (lines 227, 231)           │   (236)   (303)
                                                 └─► build-global-artifacts ────┘
                                                     (line 181)
```

- The tag filter is `claudevs-cli**[0-9]+.[0-9]+.[0-9]+*` (generated line 45). `airsl` shows a
  namespace filter ignoring its library tags: its tags include `airsl-v0.1.0` to `airsl-v0.1.4` and
  `airsl-cli-v0.1.4` (`gh api repos/airsstack/airsl/tags`), and its only GitHub release is
  `airsl-cli-v0.1.4`.
- `host` lists `custom-claudevs-cli-smoke` under `needs` and requires its result to be `success` or
  `skipped` (generated lines 241, 243).
- `dist plan --tag=claudevs-cli-v0.1.0` announced only `claudevs-cli 0.1.0`.
- A tag naming the wrong version stops at the plan: `dist plan --tag=claudevs-cli-v9.9.9` printed
  "claims we're releasing claudevs-cli 9.9.9, but that package is version 0.1.0" and exited 1.

Pull requests run this workflow in full. `publishing` is `!github.event.pull_request` (generated line
55), so they create no GitHub Release. The `Attest` step has no `if` (generated lines 155-158), so pull
request builds do attest. The generated trigger has no path filter (line 42), so plugin-only pull
requests build all six archives too. The author accepted this cost. The five most recent
`buildl-cli-release.yml` runs took between 4m30s and 9m52s, by their `createdAt` and `updatedAt`
(`gh run list -R airsstack/buildl --workflow buildl-cli-release.yml -L 5`).

Generated jobs hardcode `ubuntu-22.04` (generated lines 50, 185, 246), and it and `ubuntu-22.04-arm` are
"fully unsupported by April 17th, 2027", with brownouts before then
(`gh api repos/actions/runner-images/issues/14254`). This spec keeps them, the same as `airsl` and
`buildl`. Moving off them is later work, by a `github-custom-runners` entry or a newer dist.

`dist plan` lists the installer as `claudevs-cli-installer.sh`. No other release can become "latest"

The candidate loop gains `~/.local/bin`, first, in the same line across all ten files that carry it:

```sh
for candidate in "$HOME/.local/bin/airsl" "${CARGO_HOME:-$HOME/.cargo}/bin/airsl" "$HOME/.cargo/bin/airsl"; do
```

```
plugins/claudestacks/hooks/            comm-check enforce handoff-check preflight rearm style
plugins/claudestacks/scripts/          install-airsl.sh
plugins/claudestacks-sdlc/scripts/     attention status
plugins/claudestacks-journal/scripts/  session-start
```

`grep -rl 'for candidate in .*cargo.*bin/airsl' plugins | wc -l` printed `10`, and `grep -rl airsl
plugins --include='*.sh' --include='*.json'` returned those same ten files and no others, so no wrapper
uses a different form. Every `hooks.json` command that runs a script goes through one of them
(`plugins/claudestacks/hooks/hooks.json:9,18,26,46,57,66,70,81,85,96,104`,
`plugins/claudestacks-sdlc/hooks/hooks.json:8`, `plugins/claudestacks-journal/hooks/hooks.json:9`).

**"Every hook and script" in the intent means these ten files.** Skills are different: 23 Markdown files
under `plugins/` run a plain `airsl` (`grep -rln 'airsl run\|airsl test\|airsl check' plugins --include='*.md'
| wc -l` printed `23`, for example `plugins/claudestacks/skills/statusline/SKILL.md:79`), so they need it
on `PATH`. The installer's profile edit serves them (section 6).

The comments naming only `~/.cargo/bin` as the reason for the fallback change to name both directories:
`comm-check.sh:12`, `enforce.sh:17`, `rearm.sh:10`, `style.sh:13`, `handoff-check.sh:13`,
`status.sh:4`, `attention.sh:4`, `session-start.sh:14`, `install-airsl.sh:46`, and
`plugins/claudestacks/scripts/statusline-install.lua:71`.

Probe on a copy of `preflight.sh` with that line applied and `$HOME` replaced by a temp directory,
`CARGO_HOME` and `AIRSL_BIN` unset:

| `airsl` is in | `PATH` | Resolved |
|---|---|---|
| `~/.local/bin` only | excludes both | `~/.local/bin/airsl` |
| both | excludes both | `~/.local/bin/airsl` |
| both | includes `~/.cargo/bin` | `airsl` from `PATH` (the cargo copy) |
| `~/.cargo/bin` only | excludes both | `~/.cargo/bin/airsl` |
| neither | excludes both | none, and the `STATUS: the airsl runtime was not found` warning prints |

Unmodified, the same copy with `airsl` only in `~/.local/bin` and off `PATH` printed that warning. On
`PATH`, it did not.

`~/.local/bin` comes first because `install-airsl.sh` stops updating the cargo copy, so a cargo-first
order would keep an existing user on a stale binary after every re-run.

Unset `HOME` behaves as the existing candidates do. Without `set -u`, the candidate expands to
`/.local/bin/airsl` (probe printed `[/.local/bin/airsl]`), which fails `-x` and is skipped. None of the
nine wrappers has `set -u` or `set -e` (`grep -n 'set -[ue]'` over them printed nothing and exited 1).
`install-airsl.sh:12` has `set -u` and already reads `$HOME` at `:36`, so it stops with `HOME: unbound
variable` as it does today.

`AIRSL_BIN` and `PATH` keep their priority over the candidates (`preflight.sh:24-27`).

## 6. `install-airsl.sh`

```
start
  │
  ├─ downloader: curl if present, else wget ── neither ───────┐  reason A
  │                                                           │
  ├─ mktemp -d, fetch pointer whole to a file ─────── fail ───┤  reason B
  │  https://airsstack.github.io/airsl/install.sh             │
  │                                                           │
  ├─ sh <that file> ───────────────────────────────── fail ───┤  reason B
  │                                                           ▼
  │                                                  cargo on PATH?
  │                                                   │ yes       │ no
  │                                                   ▼           ▼
  │                         fallback line, cargo install          message for
  │                         airsl-cli --locked [--force]          that reason
  │                              │ fails ─► exit 1                exit 1
  ▼                              ▼
find_airsl ── found ─► report, exit 0
    └── not found ─► "not found" message, exit 1
```

The fetch:

- `curl --proto '=https' --tlsv1.2 -sSfL` if `curl` is present, else `wget -qO-`, the same choice and flags
  as `airsl/install/install.sh:34-42`. A `curl` that fails goes to the fallback, not to `wget`.
- The fetch is held whole before anything runs, so a failed fetch runs nothing, the rule at
  `buildl/skills/install.sh:144-152`. `-f` keeps an HTTP error page from being saved and run.
- A `mktemp` failure counts as a failed fetch. The temp directory is removed on exit.
- The pointer exists: `curl` on it returned 200, and its bytes equal `airsl/install/install.sh`.

The installer, read from `airsl-cli-installer.sh` and not executed during design. Section 8's live job
runs it in CI:

- It exits 1 on a platform with no download. `err` ends in `exit 1` (`:1701-1710`), reached from `:660`
  and `:663`.
- It checks each archive's checksum, which it carries inline (`:228-229`).
- It has no version short-circuit: `grep -n 'already\|up to date'` hits only environment-file and rc-file
  checks (`:831`, `:895`, `:1166`, `:1219`, `:1222`, `:1254`).
- Its default of editing shell profiles stays, because of the skills in section 5. Its variables, for
  example `AIRSL_CLI_NO_MODIFY_PATH` (`:51`), pass through the environment.

The script takes the latest `airsl`. The pointer defaults to the latest release
(`airsl/install/install.sh:45,49-51`), which keeps the unpinned stance `CLAUDE.md:214-215` records.

`--force` stays accepted. It applies only on the cargo route, as it does today (`install-airsl.sh:91-95`).
`cargo install` failing exits 1, showing cargo's own error, as today (`:92,94`).

Messages, in full:

| When | Text |
|---|---|
| Reason A, no `cargo` | `airsl could not be installed: neither curl nor wget is available. Install one and re-run this script, or install Rust from https://rustup.rs and re-run it.` |
| Reason B, no `cargo` | `airsl could not be installed: the prebuilt install did not complete (see the error above). Re-run this script, or install Rust from https://rustup.rs and re-run it.` |
| Falling back | `the prebuilt install did not complete; building airsl with cargo instead`, or for reason A `neither curl nor wget is available; building airsl with cargo instead`, then the "builds ~79 crates" notice (`:80`) |
| Not found after install | `the install reported success, but airsl is still not resolvable. Set AIRSL_BIN to the binary's full path.` |
| Off `PATH` | `WARNING: <dir> is not on this shell's PATH. Plugin hooks still find airsl there, but skills that run airsl directly need it on PATH. Open a new shell, or add <dir> to PATH.` |
| Shadowed | `WARNING: this install went to <installed>, but <resolved> is what hooks will run. Remove <resolved>, or put <installed> first.` |

The off-`PATH` text replaces `install-airsl.sh:62-64`, whose "they may still see nothing" becomes false once
section 5 applies. "Open a new shell" holds on the prebuilt route because the installer writes rc files
(`airsl-cli-installer.sh:1210-1222`).

The shadowed warning compares the resolved binary with the path just installed:
`$HOME/.local/bin/airsl` on the prebuilt route, `${CARGO_HOME:-$HOME/.cargo}/bin/airsl` on the cargo route.
It covers a stale copy in either direction. It is skipped when `AIRSL_BIN`,
`AIRSL_CLI_INSTALL_DIR`, `CARGO_DIST_FORCE_INSTALL_DIR` or `AIRSL_CLI_UNMANAGED_INSTALL` is set
(`airsl-cli-installer.sh:753-761`), because the user chose the location then.

The header comment (`:4-8`), the `CRATE` comment (`:14-16`) and the cargo comments (`:68-72`, `:83-90`)
are rewritten to describe both routes. Their reasoning for `--locked` stays with the cargo route.

`preflight.sh:47`, the message used when the script's own directory cannot be resolved, changes to
`curl -LsSf https://airsstack.github.io/airsl/install.sh | sh`.

`cargo make install-airsl` stays on cargo (`Makefile.toml:448`). It serves contributors and CI, which
have Rust (`.github/workflows/lua.yml:80,112`). A contributor with an older `~/.local/bin/airsl` and the
cargo directory off `PATH` would still run the older copy. That task prints no warning for it, and this
spec accepts that: contributors have `PATH` set up for `cargo`.

## 9. Errors and edge cases

| Situation | What happens |
|---|---|
| A smoke step fails on a PR | The Release check fails on that PR; no GitHub Release is created |
| A smoke step fails on a tag | `host` does not run (section 2), so no GitHub Release exists; crates.io already has the version |
| `host` or the release upload fails after smoke passes | The tag and crates.io stand with no GitHub Release |
| Recovery from either | First `gh run rerun <run-id> --failed`, which reruns failed jobs (`gh run rerun --help`). If it still fails, fix forward with a new patch version, because a crates.io version cannot be replaced (`RELEASING.md:57-58`) and `/release` publishes before it tags (`RELEASING.md:49-54`). `RELEASING.md` states this |
| Tag version differs from `Cargo.toml` | `dist` stops at plan (section 2). `/release` cannot produce this: it derives the tag from the version |
| `claudevs-v*` or `airsclaude-v*` tag | Does not match the filter (section 2); no run starts |
| Install URL before the first release | The installer download returns 404 (`curl` on `.../releases/latest/download/claudevs-cli-installer.sh` returned `404`), and the pointer prints `could not download` and exits 1 (`buildl/install/install.sh:66-71`) |
| `CLAUDEVS_VERSION=v9.9.9` | The `v` is stripped. On `buildl`'s copy: "could not download the installer for buildl 9.9.9; is 9.9.9 a released version?", exit 1 |
| `CLAUDEVS_VERSION=1;2`, space, `../x` | Refused before any fetch, exit 1 (section 8) |
| `CLAUDEVS_VERSION` empty | Treated as latest: `${BUILDL_VERSION:-latest}` (`buildl/install/install.sh:45`) |
| A user without `git` | `claudevs check` on a plugin with cases exits 2, with the error in section 1. Install docs state the requirement |
| `claudevs check` on a missing path | Exit 2: ``claudevs: walk plugin `.../no-such-plugin`: No such file or directory (os error 2)`` |
| Windows | No target, no installer (section 1) |

## 10. Unproven until the first pull request

These are not claims. Only a real runner or a real Alpine can answer them, and the author ruled out running
Docker for the proof. The first pull request's Release check answers the first three:

- The binary builds and runs on `macos-15`. dist's plan accepts the runner (section 2).
- The musl binary runs on Alpine. `airsl` runs its musl archives there with Lua
  (`airsl/.github/workflows/airsl-cli-smoke.yml:50-51,133-138,179-180`), and `mlua-sys` is the only
  native dependency here. The two `mlua-sys` versions were not compared.
- The wiring fixtures pass on Alpine. They were proven with only `sh` on `PATH`, on macOS.

Two more are not answered by that check:

- The install URL completing on stock Alpine, including its `wget` branch and unpacking `.tar.xz`. Smoke runs
  archives, not the installer, and an installer cannot be fetched from a release before it exists. The
  first real run on Alpine is a person's.
- `actions/attest` on a pull request from a fork. The generated file notes that fork PRs lack secrets
  (generated lines 74-77). If it fails, outside contributors' PRs show a red Release check.

**If the first PR's Release check fails on any of these**, the PR is not merged. The target and the smoke step
stay as this spec has them, nothing is dropped to get a green check, and the author decides what happens
next. The `triage` skill turns the failure into a new intent. This happens after the chain's plans finish,
because `execute` does not push unless told to
(`plugins/claudestacks-sdlc/skills/execute/SKILL.md:91`), so it is not recorded as a plan deviation.

The accepted gap: the `claudevs` Lua test stage never runs on a musl build, so a bug affecting only that
build could ship while the other four platforms pass the full set.

## 12. Non-goals

- Windows support, for `claudevs` or its installer.
- Binaries or installers for `airsclaude` or `claudevs`.
- Changes to the `airsl` repository or its releases, including its `macos-14` runner.
- New `airsclaude` or `claudevs` versions.
- A `git` probe in `claudevs doctor`.
- A self-updating `claudevs`: `install-updater = false`.
- A site beyond `install.sh`.
- Moving `cargo make install-airsl` or CI off cargo.
- Moving off `ubuntu-22.04` before its retirement.
